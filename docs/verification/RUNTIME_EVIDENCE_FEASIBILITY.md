# Developer-owned runtime evidence: BGA-425 decision


Decision observed 2026-10-07 UTC: **defer a new MCP report-reading capability**.
Existing agent shell, test-runner and XML tools produced and inspected the real
outputs below without a new MCP surface. No observed benefit justifies admitting
an additional reader now. This completes a bounded research decision; it does
not implement or verify a runtime-evidence capability. No implementation owner
is created for an approach that has not been accepted.

## Value and supported conclusions

The real tests cover local turns/drafting, persistence/reload, scoring and end
conditions. Integration tests use local framework doubles. Client tests use a
controlled DOM and framework object. Neither establishes live BGA compatibility,
actual database behavior, complete gameplay or untested UI behavior. The source
identity for the private experiment is known externally; a general future reader
cannot infer it from a native JUnit file.

The existing agent tools already provide execution status, selected command,
source snapshot, runner digest and original-project immutability. Independent XML
inspection yields counts and format-specific outcomes. A passive MCP reader would
add another parser and output boundary while supplying less provenance unless a
producer envelope and useful agent workflow are first demonstrated. This is the
reason for deferral. OTR is a feasible format to investigate later; the JUnit
finding does not justify rejecting all report formats.

## Requirements before accepting a future reader

A later decision must first demonstrate a useful workflow beyond the existing
agent tools and create a permanent implementation owner for the accepted subset.
The contract must name the actual producer/version and format, project identity,
tested source and generated-build manifest, invocation and selected/expected case
inventory, execution start/end, scenario/assertion meaning and completeness.
Independently observed provenance must be distinguished from producer assertions.
Missing or unverifiable source/build identity remains unknown; successful selected
cases cannot imply complete coverage.

Passed, failed, errored, skipped and incomplete are separate outcomes. Unknown
format-specific status, unfinished execution or missing terminal events remain
incomplete/unknown. Staleness is a separate identity/freshness relationship, not a
new test outcome: compare independently bound source/build bytes and explicit
freshness policy. Malformed or count-inconsistent reports must be refused. No
status, timestamp, digest field or signature of an untrusted producer authorizes
instructions, network operations or project execution.

Any reader must use the existing policy boundary for explicitly configured-root
confinement, symlink refusal, cancellation and bounded reads. A proposed initial
subset should refuse reports over 1 MiB or 1,000 testcase records, XML entities,
DTDs, external references and unsupported encodings/versions. Parsing must obey
the shared tool deadline and cleanup budget. These are proposed constraints, not
implemented security claims. Output should default to aggregate statuses and
opaque case references, with paths, arbitrary names, assertion text, exception
stacks, host/user and environment metadata, attachments, properties and raw
stdout/stderr withheld. Existing redaction
and final output limits still apply to every publication surface. Secret-pattern
redaction alone cannot prove arbitrary report text safe.

Reports remain untrusted data. No instruction embedded in them is followed; no
URL is fetched, referenced file opened or attachment executed. Retention requires
explicit developer control and sanitized receipts; private game source, player
data and credential-bearing logs cannot enter public fixtures, package artifacts
or CI. Negative installed-command cases, source-binding controls and privacy
proof are required before admitting any future capability.

Test execution stays with the agent's existing tools. New MCP subprocess,
browser, network or Studio operations need a separate explicit scope and threat
model decision. BGA-308 through BGA-311 retain Studio runtime-operation ownership;
BGA-312 retains log ownership. This research neither resolves their live access
holds nor authorizes new operations. No source was uploaded or published.
