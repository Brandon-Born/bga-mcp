# Threat model

Reviewed: 2026-08-09. Backlog items: BGA-013, BGA-018.

This document is the human-readable view of [`config/threat-model.json`](../config/threat-model.json), which is the machine-checked source of truth. `pnpm verify:threat-model` compares the two cell for cell: every field carried by both files — asset and actor descriptions, boundary gates, review dates, status and preconditions, abuse-case actors, assets, surfaces and mitigations, mitigation titles, control, status, surfaces, owner, cadence and evidence, and each residual risk's abuse cases and acceptance — must be identical, and the gate seeds a disagreement in each of them before it reports. `pnpm verify:scenarios` reserves scenarios for planned controls and requires implemented automated controls to have executable coverage.

Everything both files share is therefore in a table. Prose here explains a decision; it never carries state, because prose cannot be compared.

## Scope

The model covers the shipped server (`bga-mcp` over stdio), its configuration, its verification harness, and the release supply chain. Documentation retrieval is implemented behind explicit network permission, own-account Studio log reading is discoverable as experimental, and Studio synchronization remains planned; all three external paths are included because their boundaries decide what may ship.

## Assets

| ID                       | Asset                                       | Why it matters                                                                                                                                                                |
| ------------------------ | ------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ASSET-LOCAL-SOURCE       | Local BGA project source                    | Game code, database definitions, and options inside a configured project root.                                                                                                |
| ASSET-LOCAL-PRIVATE      | Local files outside the project roots       | SSH keys, environment files, browser profiles, and unrelated repositories on the developer machine.                                                                           |
| ASSET-STUDIO-CREDENTIALS | BGA Studio credentials                      | SSH keys, agent sockets, and session material that authenticate to BGA Studio.                                                                                                |
| ASSET-STUDIO-PROJECT     | Remote Studio project                       | Shared, hard-to-restore files, tables, and saved state belonging to a Studio project; the observed default readonly ACL can expose project source to other Studio developers. |
| ASSET-PLAYER-DATA        | Player data                                 | Player identities and gameplay records reachable through Studio logs or tables.                                                                                               |
| ASSET-RELEASE-ARTIFACT   | Release artifacts and verification evidence | The published package, CI logs, coverage output, conformance output, and evidence files.                                                                                      |
| ASSET-CLIENT-CONTEXT     | MCP client context                          | The agent context window and the actions an agent takes based on server output.                                                                                               |

## Actors

| ID                           | Actor                               | Trust        | Why that level                                                                                                                                           |
| ---------------------------- | ----------------------------------- | ------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ACTOR-DEVELOPER              | BGA developer                       | trusted      | Runs the server, chooses its configuration, and owns the machine.                                                                                        |
| ACTOR-MCP-CLIENT             | MCP client or agent                 | semi-trusted | Sends tool arguments that may be model-generated, malformed, or unintended.                                                                              |
| ACTOR-PROJECT-CONTENT        | Project file content                | untrusted    | File names, links, and text inside a project root, possibly authored by a third party.                                                                   |
| ACTOR-DOC-CONTENT            | Documentation and community content | untrusted    | Retrieved BGA Studio documentation, wiki pages, and community examples.                                                                                  |
| ACTOR-STUDIO-SERVICE         | BGA Studio service                  | semi-trusted | Remote SFTP and web endpoints whose responses the server would parse.                                                                                    |
| ACTOR-OTHER-STUDIO-DEVELOPER | Other BGA Studio developer          | untrusted    | A separate developer account that must not gain access to the dedicated private test project's source through the observed default readonly-sharing ACL. |
| ACTOR-DEPENDENCY             | Dependency and CI supply chain      | semi-trusted | npm packages, GitHub Actions, and the package manager used to build and publish.                                                                         |

The client is only semi-trusted on purpose. Tool arguments may be model-generated, so the server must treat them as hostile input even when the developer is trusted.

An unreviewed boundary is a shipping gate, not a note. A reviewed boundary is not a verification claim either: it records the controls known at the review, and the two columns that decide what may cross it — its preconditions and the surface coverage below — are compared against the record rather than described here.

`Crossed by` says which capabilities are judged against a boundary. Most are judged against the capabilities that name them. TB-OUTPUT is `every-capability`: every tool result and every error leaves through it whether or not a capability names it, so its open output surfaces apply to all of them.

The review dates are the dates of the reviews themselves. The five boundaries dated 2026-08-06 were established with the initial threat model; documentation retrieval and both Studio boundaries were reviewed on 2026-08-07 and are recorded in the [documentation boundary review](verification/DOCS_BOUNDARY_REVIEW.md) and the [Studio boundary review](verification/STUDIO_BOUNDARY_REVIEW.md). The 2026-08-08 adversarial review found `TB-DOCS-NETWORK` recorded as `reviewed` in one file and `unreviewed` in the other, and the gate of the day passed the contradiction because it compared identifiers rather than fields. That is the defect this document's shape now answers.

TB-STUDIO opens file synchronization behind eight preconditions, including an explicit disabled cross-developer readonly ACL on the dedicated private project. The 2026-08-08 live setup proved that selecting `Private` does not satisfy that condition by itself: BGA enables readonly source sharing by default. Log access remains a separate experimental own-account read boundary. See BGA-322.

## Output surfaces

Protected data does not leave through one door. A control that covers the MCP result and nothing else is not a control that protects the data, so every place the server can publish is recorded, and every abuse case that publishes protected data names the surfaces it can reach.

| ID                     | Surface                        | What reaches it                                                                                                   |
| ---------------------- | ------------------------------ | ----------------------------------------------------------------------------------------------------------------- |
| SURFACE-TOOL-RESULT    | Successful MCP result          | Text content and structured content of a tool or resource result that succeeded.                                  |
| SURFACE-TOOL-FAILURE   | Published failure result       | The message, code, and details of a refusal, a validation failure, or an unexpected error returned to the client. |
| SURFACE-CLI-STDOUT     | Terminal diagnostics           | What the command-line entry point prints for an operator, including the Studio preflight report.                  |
| SURFACE-PROCESS-STDERR | Server log and launcher stderr | Every line the process writes to stderr, which an MCP launcher captures into its own log file.                    |
| SURFACE-CI-ARTIFACT    | Retained artifact              | Verification evidence, packaged-run records, and anything else a CI job uploads or keeps.                         |

## Operator responsibilities

- Start the server with the narrowest `--project-root` set that makes the work possible.
- Leave `--allow-network`, `--allow-mutations`, and `--allow-remote-project` unset unless the task needs them, and unset them afterwards.
- Treat any server result as content that may reach a remote agent provider.
- Rotate any credential that appears in a transcript or artifact, then report the leak through [SECURITY.md](../SECURITY.md).

## Review triggers

Re-review this model, and record the result here, when any of the following happens:

- A capability crosses TB-DOCS-NETWORK or TB-STUDIO for the first time.
- The policy boundary gains a new decision point or a new configuration flag.
- A new external adapter, transport, or credential provider is introduced.
- A dependency with filesystem, network, or subprocess reach is added.
- A new way for the server to publish anything appears, because it is a new output surface.
